# Linezheets Core-Functions Fault Audit
**Date:** 2026-06-09 · **Scope:** the 8 core functions, audited as 10 domains
**Method:** 10 domain-specialist agents read the live Next.js `app/api` + `lib/` code; every candidate fault was then independently re-checked against the real code by an adversarial verifier. **73 of 81 candidates confirmed** (8 rejected as false positives).

> **Authoritative surface:** the deployed system is the **Next.js app** (it owns the Vercel crons and the Docker/Railway standalone build). The Express `backend/` directory is **dead code that is never mounted** — but it often contains the *correct* logic the Next.js path is missing (server-side price recompute, stock validation). Several faults are "the safe implementation exists but isn't the one running."

## The faults cluster into 14 root causes

Many of the 73 findings are the *same bug* seen from different domains. Fixing by root cause is far cheaper than fixing 73 line items.

### 🔴 MONEY-PATH (deploy fixes first — direct, unbounded loss)

**A. Order total is client-controlled — never recomputed server-side.** `D3-1, D7-1, D9-1, D10-1` (+ dead-code `D3-6, D7-8`)
A buyer can POST `total_usd: 1` for a $50,000 order. The order is accepted, stock allocated, Stripe charges $1, the invoice prints $1, and escrow pays the brand based on $1 — while real goods ship. Accepted price *offers are never bound to the order* either, and `currency` is also client-set. **This is the single highest-impact hole.**

**B. Installment "paid" + premature escrow release.** `D3-2, D4-2, D4-7, D4-8, D8-1, D10-4`
A single succeeded installment flips the whole order to `paid`. `releaseEscrow` then transfers the **full** `total_usd` (not the amount actually collected). On a 30/70 plan, a delivered order pays the brand 100% after the buyer paid 30% — the platform funds the gap and eats buyer-default risk. The webhook's installment split also has no rounding-remainder handling, and `create-intent` charges the *full* total on installment 1 then schedules more (double-collection).

**C. Multi-brand order misroutes the entire payout.** `D4-1, D8-3, D3-8`
`releaseEscrow` pays `items[0].brand_name` the full order total; other brands in the same order get nothing. Authorization (view/patch/deliver) is keyed on `items[0]` / array-contains, so the wrong brand can see and act on the order. Fix = enforce **one brand per order** (simple) or split escrow per brand (full).

**D. Escrow release is not atomic and has no Stripe idempotency key → double payout.** `D4-3, D8-4, D10-3`
Two release paths (status-PATCH auto-release and manual `/payments/release`) both read `escrow_status='held'`, both create a transfer. No row-claim, no `idempotencyKey` → the brand can be paid twice.

**E. Buyers can be double-charged.** `D4-4, D3-5, D10-2`
The installment **cron has no idempotency key and no status-claim** → a retried run re-charges every still-`pending` row. `create-intent` isn't idempotent (double-submit = double charge). The Stripe **webhook has no event-dedup** → replayed events re-schedule installments and duplicate billable rows.

**F. Funds release before goods are delivered, with no clawback.** `D8-2, D8-5, D4-5`
A brand self-certifies `delivered` (no proof, no carrier signal) and triggers irreversible release. No status-transition validation (`new → delivered` is allowed). Refund/dispute resolution never reverses the transfer or claws back commission, and there's no hold window.

### 🟠 DATA INTEGRITY / ACCESS

**G. AI-upload & linesheet import can corrupt other brands' data.** `D1-1, D1-2, D1-3, D1-5, D6-2, D6-3`
`inventory.sku` is **globally unique** and commit upserts `onConflict: 'sku'` with no brand scoping — Brand B's upload overwrites Brand A's live product. `brand_name`/`brand_id` come from the **untrusted payload**, not the authenticated user (tenant spoofing). The human-approval gate is **client-side only**; the commit endpoint accepts arbitrary JSON. An error-path `delete().in('sku', …)` can destroy other brands' rows. The linesheet route writes a **UUID into an INTEGER `brand_id`** column (import fails or orphans rows).

**H. Import price/value parsing & validation is unsafe.** `D1-4, D1-6, D1-8, D1-10, D2-3, D2-4, D6-1, D6-7`
`parseFloat("$1,200")` → `0`; `parseFloat("1,200")` → `1` — a $1,200 item silently stored as $1, buyable at 0.1% of price. No AI-output schema/enum validation (prompt-injectable from file contents). Negative prices persist. Imported products get **all-zero `sizes` with non-zero `stock_total` → unsellable**. WSP↔SRP derivation ratio is inconsistent across paths (0.5 / 0.45 / 0.40).

**I. Headline features POST to routes that don't exist.** `D2-1, D2-2`
"AI Mass Upload → Import N Products" POSTs to `/api/products/bulk` (**doesn't exist**) → always fails. Margin Settings PATCHes `/api/brand/settings` (**doesn't exist**) → margin/markup/terms are never saved.

**J. Confidential pricing leaks / retail mispricing.** `D2-5, D2-6`
Public marketplace API returns **`wsp_usd` (wholesale cost) to unauthenticated callers** — anyone can scrape every brand's buy price. One Shopify sync path publishes products **at wholesale cost** instead of retail.

**K. Communication privacy & offer tampering.** `D9-4, D9-2, D9-3, D9-6, D4-10, D7-3`
Chat RLS exposes **all guest sessions to every user** (IDOR). `PATCH /offers/[id]` blind-merges arbitrary fields → a buyer can self-accept and rewrite the price. Offers accept negative/NaN totals. Brands can't see disputes on their orders; sellers can't fetch their own invoice.

### 🟡 DOCUMENTS / CURRENCY / NOTIFICATIONS

**L. Currency is mishandled in money-bearing documents.** `D5-7, D7-6, D5-6, D7-5, D7-7, D10-6`
`formatCurrency` uses `maximumFractionDigits: 0` — **drops cents** (already live in the buyer cart PDF). Invoices/emails hard-code `$`/USD and read `total_usd` regardless of order currency. The cart PDF sums multiple currencies into one USD-labeled total. FX falls back silently to stale hard-coded rates.

**M. Documents aren't customs/accounting compliant.** `D7-2, D7-4, D8-6, D8-7`
Invoice/packing list omits HS code, country of origin, net/gross weight, package count, Incoterms, declared value, tax line, seller EORI/legal address — **shipments can be held at the border**. Invoice number is a millisecond timestamp (collision-prone). Tracking number/carrier stored as free-text in `notes`.

**N. Email triggers are incomplete or misrouted.** `D5-1, D5-2, D5-3, D5-4, D5-5, D5-8, D5-9, D5-10`
No dispatch/delivered email (template exists, never used). No escrow-release email. Payment-received/failed emails go to **admin only** — buyer and brand are never told. Dispute open/resolve notifications are dropped for whole classes of users. Promised NET-terms reminders don't exist.

### Operational
**O. Import job durability.** `D6-4, D6-5, D6-6` — fire-and-forget background import has no sweeper (jobs hang in `processing` forever on serverless freeze), swallows errors, and has no file-size cap.

## Recommended remediation sequence

| Wave | Theme | Why this order |
|---|---|---|
| **P0 — money bleed** | A → E → D → B → C | A is unbounded loss on every order; E/D/B/C are duplicate/over payouts. Ship as one hardening release. |
| **P1 — integrity/access** | G → H → I → J → K → F | Stop cross-tenant corruption and confidential leaks; make the upload/margin features actually work; add delivery proof + clawback. |
| **P2 — docs/currency/notify** | L → M → N → O | Customs compliance, correct money display, full notification matrix, job durability. Then delete dead `backend/` routes to remove the "safe path that isn't running" trap. |

**Suggested cross-cutting primitives to build once and reuse:**
1. A server-side **authoritative pricing function** (looks up `wsp_usd` by SKU inside the stock-allocation RPC) — kills Theme A everywhere.
2. A **`stripe_webhook_events` dedup table** + deterministic Stripe `idempotencyKey`s — kills Theme E.
3. An **atomic escrow claim** (`UPDATE … SET escrow_status='releasing' WHERE escrow_status='held' RETURNING`) + per-brand, collected-amount-based payout — kills C/D and the release half of B.
4. A shared **money parser** (`parseMoney`) and a **2-decimal `formatCurrency`** — kills H's price-parse bugs and Theme L.
5. A **one-brand-per-order** constraint at checkout — collapses C to a validation check.

# Appendix — all 73 confirmed findings (full detail)

## D1-ai-upload — AI mass upload & DB protection
*Confirmed 8/10.* The smart-sync flow: (1) POST /api/upload/smart-sync parses a CSV/XLSX/PDF, runs a fuzzy column mapper (lib/smart-sync/mapper.ts + column-maps.ts) or sends the PDF to Claude, and returns staged "products" to the client; (2) a human reviews in the dashboard; (3) POST /api/upload/smart-sync/commit upserts the products into the public.inventory table. Overall health: POOR for a money-handling marketplace. The single most serious problem is that inventory.sku carries a GLOBAL unique constraint (not per-brand) while the commit route upserts onConflict:'sku' with no brand ownership check and copies brand_name from the untrusted client/AI payload — so one brand committing a colliding SKU silently overwrites another brand's live product, and the RLS write policy (FOR ALL, auth.role()='authenticated') does nothing to stop cross-tenant writes. The human-in-the-loop gate is purely client-side; the server /commit endpoint accepts any products JSON with no approval token. Price/quantity coercion uses bare parseFloat with no currency/comma stripping and no non-negative clamp, so "$1,200" becomes 0, "1,200" becomes 1, and negative WSPs reach the DB. The legacy Express backend/routes/upload.js diverges materially (duplicate object key drops name→description mapping; 'price' maps to retail; /confirm is unauthenticated and writes nothing). These are real correctness/financial/authorization faults, not style.

### 🟠 D1-1 — Commit upserts on globally-unique SKU with no brand scoping — one brand overwrites another brand's live products
- **Severity:** high  ·  **Category:** authorization/data-integrity  ·  **Confidence:** high
- **Location:** `app/api/upload/smart-sync/commit/route.ts:80-100`
- **Fault:** inventory.sku has a GLOBAL unique constraint (000_consolidated_schema.sql:26 `sku TEXT UNIQUE`; 003_inventory_realign.sql:104 `ADD CONSTRAINT inventory_sku_unique UNIQUE (sku)`; 001_inventory.sql:80). The commit route does `sb.from('inventory').upsert(withSku, { onConflict: 'sku', ignoreDuplicates: false })` with NO filter on brand_id/brand_name and never verifies that an existing row with that SKU belongs to the authenticated brand. SKUs in fashion linesheets are commonly short/generic (e.g. 'BLZ-001', '1234', or auto-generated 'SKU-0001' per mapper.ts:316-320). When Brand B commits a product whose SKU collides with Brand A's existing SKU, the upsert OVERWRITES Brand A's row (price, stock, images, brand_name) with Brand B's data. By contrast the single-product create path scopes correctly (app/api/products/route.ts:32 `.eq('brand_name', sf.brand_name)`), proving the intended model is per-brand.
- **Impact:** Cross-tenant data destruction: a brand can silently overwrite or hijack another brand's live catalog rows — wrong prices/stock shown to buyers, orders placed against corrupted data, and the victim brand's products effectively reassigned. Direct money and data-integrity loss.
- **Fix:** Resolve the authenticated user's brand first (admin.from('brand_storefronts').select('brand_name, brand_id').eq('user_id', user.id).maybeSingle()), exactly as app/api/products/route.ts does, and FORCE brand_name/brand_id to the owner's value on every row before writing (ignore any brand_name in the payload). Then either (a) change the DB constraint to UNIQUE(brand_id, sku) (or brand_name, sku) and upsert with onConflict on that composite key, or (b) keep global SKU but, before upsert, query existing rows for the incoming SKU list and reject/skip any SKU already owned by a DIFFERENT brand (return them in the errors array). Also fix the error-fallback at route.ts:92-97: the blind `delete().in('sku', skuList)` must be scoped to the owner's brand (`.eq('brand_name', sf.brand_name)`) or removed, since it currently deletes other brands' rows on any upsert failure. Do not rely on RLS — the inventory_write_authenticated policy grants FOR ALL to any authenticated user with no brand scoping; tightening that policy to scope writes by brand would also help as defense in depth.
- **Verified:** Confirmed against current code. (1) The global UNIQUE(sku) constraint is real: 000_consolidated_schema.sql:26 `sku TEXT UNIQUE` and :155 `ADD CONSTRAINT inventory_sku_unique UNIQUE (sku)`; 001_inventory.sql:10,80; 003_inventory_realign.sql:104; 004_cleanup.sql:145. No composite UNIQUE(brand,sku) exists anywhere. (2) The commit route upserts on the bare sku with no brand scoping or ownership check: route.ts:86-89 `sb.from('inventory').upsert(withSku, { onConflict: 'sku', ignoreDuplicates: false })`. The only auth check is route.ts:52-53 (user non-null); it never resolves the user's brand storefront, unlike products/route.ts:53-59 which looks up sf.brand_name and FORCES inventory.brand_name = sf.brand_name on insert (line 99). In the commit route, brand_name/brand_id come straight from the uploaded payload (mapper.ts:348 reads brand_name from the row; route.ts:71 uses p.brand_name) and are never overwritten to the owner's value. (3) RLS does NOT mitigate: the route uses the user-scoped createClient() (anon key + session, so RLS applies), but the only write policy is `inventory_write_authenticated FOR ALL USING (auth.role()='authenticated') WITH CHECK (auth.role()='authenticated')` (000_consolidated_schema.sql:188-191; 001_inventory.sql:113-116) — any authenticated user may UPDATE any row regardless of brand. So when Brand B commits a SKU that collides with Brand A's existing row, the upsert UPDATEs Brand A's row, overwriting price/stock/images and even brand_name with Brand B's data. (4) Collisions are realistic: user-supplied raw SKUs pass through verbatim (mapper.ts:314-315); short generic SKUs are common in linesheets. Auto-generated SKUs are brand-prefixed (`brandCode-0001`, mapper.ts:317-319) which reduces auto-collision risk, but does nothing for user-supplied SKUs. Additional aggravating factor the auditor missed: the error fallback at route.ts:92-97 does a blind `delete().in('sku', skuList)` then insert, which would DELETE another brand's colliding rows outright — even more destructive than the upsert path. Minor correction to auditor wording: rows DO carry brand_name/brand_id columns, but their values are taken from the uploaded file and are NOT bound to the authenticated user — substantively the auditor is correct.

### 🟠 D1-2 — brand_name/brand_id taken from untrusted AI/client payload, not the authenticated user — tenant spoofing
- **Severity:** high  ·  **Category:** authorization  ·  **Confidence:** high
- **Location:** `app/api/upload/smart-sync/commit/route.ts:62-74`
- **Fault:** The commit handler authenticates the user (line 52-53) but then builds each row from the client-supplied product objects: brand_name is `String(p.brand_name ?? '').trim()` (line 71) and brand_id is never set at all, so it falls to the column default of 1 (000_consolidated_schema.sql:33 `brand_id INTEGER NOT NULL DEFAULT 1`). The values originate from Claude's PDF extraction or the raw spreadsheet (smart-sync/route.ts prompt asks the model to fill brand_name), and are fully attacker-controllable via a direct POST. Nothing ties the written brand_name to the signed-in account. The inventory RLS write policy only checks `auth.role() = 'authenticated'` with no brand predicate (001_inventory.sql:113-116), so the DB does not block it either.
- **Impact:** Any authenticated brand can write inventory rows under any other brand's name (or all rows collapse to brand_id=1), poisoning marketplace listings, sell-through analytics, and brand-store pages. Combined with D1-1 this is a full cross-tenant write primitive.
- **Fix:** In commit/route.ts, after authenticating, resolve the caller's storefront server-side exactly like products/route.ts:53-59 (query brand_storefronts by user.id; 404 if absent). Then on EVERY row force brand_name = sf.brand_name and brand_id = the owner's id, overwriting/ignoring any client-supplied brand_name/brand_id. Also remove 'brand_id' (and ideally 'brand_name') from the DB_COLUMNS passthrough whitelist so client values can never leak through sanitise. Backstop at the DB: tighten the inventory_write RLS WITH CHECK to scope writes to the owning brand (e.g. join brand_storefronts on auth.uid()) instead of the blanket auth.role()='authenticated'. Severity high rather than critical only because exploitation requires an authenticated brand account and the brand_id space is small integers; impact (cross-tenant listing/analytics poisoning) is otherwise as described.
- **Verified:** Confirmed in the actual current code. In app/api/upload/smart-sync/commit/route.ts the POST handler authenticates only "is there a user" (lines 51-53: `const { data: { user } } = await supabase.auth.getUser(); if (!user) return ... 401`). It then builds every inventory row from the client-supplied `products` payload by spreading `...p` (line 63) and explicitly setting `brand_name: String(p.brand_name ?? '').trim()` (line 71) — sourced from the AI/client, never from the signed-in account. There is NO brand_storefronts lookup anywhere in this file. `brand_id` is not injected by prepareRow/sanitise, so untouched rows fall to the column default 1 — confirmed at supabase/migrations/000_consolidated_schema.sql:33 (`brand_id INTEGER NOT NULL DEFAULT 1`) and 001_inventory.sql:36. The inventory write RLS policy is exactly as cited: 001_inventory.sql:113-116 and the consolidated copy 000_consolidated_schema.sql:188-191 both define `inventory_write_authenticated ... FOR ALL USING (auth.role() = 'authenticated') WITH CHECK (auth.role() = 'authenticated')` — no brand/tenant predicate, so the DB does not block a cross-tenant write. The contrast confirms intent: app/api/products/route.ts:53-59 resolves `brand_storefronts` by `user.id` and writes `brand_name: sf.brand_name` (line 99), the server-side pattern the commit route omits. brand_name is attacker-controllable both via the AI extraction (smart-sync/route.ts:117 prompt asks the model for brand_name) and via a direct POST of arbitrary `products`. Endpoint is reachable (exported POST). Finding is real and if anything slightly understated.

### 🟠 D1-3 — Human-in-the-loop approval is client-side only; server /commit accepts arbitrary product JSON
- **Severity:** high  ·  **Category:** validation/state-machine  ·  **Confidence:** high
- **Location:** `app/api/upload/smart-sync/commit/route.ts:44-74`
- **Fault:** The owner requires human review before any DB write. The only gate is in the browser: brand-admin.html:2447-2448 disables the commit button until `window._mappingConfirmed`, and brand-dashboard.html confirmSave() posts the reviewed list. The server /commit endpoint has no notion of an approval token, staging id, or server-held staged set — it simply takes `products` from the request body (line 46) and writes them. A caller can POST any JSON array directly, bypassing review entirely. There is also no linkage to the smart-sync staging response (route.ts returns staged:true but nothing persists server-side), so the AI extraction is never re-validated at commit time.

### 🟠 D1-4 — Price coercion drops currency symbols and thousands separators (parseFloat) — $1,200 becomes 0 or 1
- **Severity:** high  ·  **Category:** financial-calc  ·  **Confidence:** high
- **Location:** `app/api/upload/smart-sync/commit/route.ts:20-22`
- **Fault:** Prices are coerced with bare parseFloat and no sanitisation: commit/route.ts:20-22 `parseFloat(String(p.wsp_usd ?? 0))`, and the spreadsheet path mapper.ts:323-324 `parseFloat(getField(row,'wsp_usd') ?? '')`. parseFloat does not strip currency symbols or grouping commas. Verified: parseFloat('1,200') === 1 (everything after the comma is discarded) and parseFloat('$1,200.50') === NaN (then `|| 0` -> 0). Spreadsheets and linesheets routinely contain '$1,200', '1,200.00', '€950'. The legacy backend correctly strips with `parseNum` = `parseFloat(String(val).replace(/[^0-9.\-]/g,''))` (backend/routes/upload.js:190-194), so the authoritative Next.js path is strictly worse.
- **Impact:** A $1,200 wholesale item is stored as $1.00 (comma case) or $0.00 (currency-symbol case). Buyers can purchase at 0.1% of true price; the brand loses the entire margin on every affected unit. Silent — no error is raised.
- **Fix:** Add a shared currency sanitiser and apply it at the INGESTION points where raw text enters, not (primarily) at commit. Concretely:
1) lib/smart-sync/mapper.ts:323-324 (and 326, 330-331, 355-356) — replace `parseFloat(getField(...) ?? '')` with a helper: `const parseMoney = (s?:string)=>{ if(s==null) return null; const n=parseFloat(String(s).replace(/[^0-9.\-]/g,'')); return Number.isFinite(n)?n:null; }`. Treat null (unparseable) as a review error rather than silently zeroing.
2) app/api/upload/smart-sync/route.ts:182-183 (PDF/Claude normaliser) — apply the same helper.
3) Keep the commit route (commit/route.ts:20-22) as a defensive net by also routing its parse through the shared helper, since the endpoint accepts arbitrary JSON and a future/non-UI caller could submit raw strings.
Note the locale caveat: a naive `replace(/[^0-9.\-]/g,'')` mishandles European decimals like "1.200,50" (would yield 1.20050) — if EU-formatted linesheets are expected, detect/normalise the decimal separator before stripping. Reject unparseable values into the skippedErrors list so reviewers catch them instead of selling at $0/$1.
- **Verified:** The underlying fault (bare parseFloat with no currency/thousands sanitisation, silently zeroing or truncating prices) is REAL, but the auditor mislocated the primary impact point. I confirmed parseFloat behavior at runtime: parseFloat('1,200')===1, parseFloat('$1,200.50')||0===0, parseFloat('€950')||0===0.

KEY CORRECTION — the CITED location commit/route.ts:20-22 is the WRONG (least-affected) spot:
- Line 20: `const wsp = parseFloat(String(p.wsp_usd ?? 0)) || 0;` line 21: `const srp = parseFloat(String(p.srp ?? 0)) || 0;`
- This route receives `products` JSON POSTed by the client (public/pages/brand-dashboard.html:2183 -> `/api/upload/smart-sync/commit`). The client builds `_reviewProducts` from the staging endpoint's output (brand-dashboard.html:2031 `(data.products||[]).map(...)`) where prices are ALREADY numeric, and the review inputs write back numbers via `oninput=...parseFloat(this.value)||0` (lines 2141/2146). So at commit, `p.wsp_usd` is a JS number; `String(1200)` -> "1200" -> parseFloat -> 1200. No corruption occurs at the cited lines in the actual app flow.

The REAL corruption point is the SECONDARY location the auditor also cited, mapper.ts:323-324:
- `const wsp = parseFloat(getField(row,'wsp_usd') ?? '') || 0;` / `const srp = parseFloat(getField(row,'srp') ?? '') || 0;`
- `getField` returns the raw spreadsheet cell as a string (smart-sync/route.ts:335 `obj[h] = row[idx] !== undefined ? ### 🟠 D1-5 — Error-path fallback deletes rows by SKU then re-inserts — destroys colliding (possibly other-brand) rows with no rollback
- **Severity:** high  ·  **Category:** data-integrity/idempotency  ·  **Confidence:** high
- **Location:** `app/api/upload/smart-sync/commit/route.ts:91-100`
- **Fault:** If the upsert errors, the fallback does `sb.from('inventory').delete().in('sku', skuList)` followed by a fresh `insert(withSku)`. There is no transaction: if the subsequent insert fails (e.g. one row violates a constraint), the just-deleted rows are gone and nothing is rolled back — a partial/total data-loss window. The whole batch insert is also all-or-nothing at the PostgREST level: a single bad row aborts the insert, so either all reviewed rows or none land, but the prior delete already executed.
- **Impact:** On any upsert error, legitimate existing inventory (including cross-brand rows) can be permanently deleted while the replacement insert fails, leaving the catalog with missing products and no recovery. Classic destructive non-atomic write.

Separately, tighten the schema: change the UNIQUE(sku) constraint to UNIQUE(brand_id, sku) and add an RLS WITH CHECK/USING predicate binding writes to the caller's owned brand_id, so a buyer/brand can never overwrite or delete another brand's inventory. If the RPC is not adopted immediately, at minimum (a) scope the fallback delete by the caller's brand_id, and (b) drop the destructive delete entirely and surface the original upsert error to the client rather than attempting a non-atomic recovery. Note severity is high rather than critical because it sits on the upsert error path, not the happy path; but combined with the global UNIQUE(sku) and brand-agnostic RLS it is a genuine cross-tenant data-loss vector.
- **Verified:** The cited code exists verbatim. app/api/upload/smart-sync/commit/route.ts lines 91-100: `if (error) { const skuList = withSku.map(r => r.sku as string); await sb.from('inventory').delete().in('sku', skuList); const { data: ins, error: insErr } = await sb.from('inventory').insert(withSku).select('id'); ... }`. Only nuance: this is on the upsert error path (line 91), so it triggers on upsert failure rather than on every request — but it is reachable and destructive when reached. The auditor's description and cited evidence are accurate.

### 🔴 D3-1 — Order total is trusted from the client — full price tampering (server never recomputes from line items)

## D4-escrow-refund-payout — Refunds, escrow release timing, payouts, disputes, cron
*Confirmed 9/10.* The Next.js payments path uses a "separate charges + transfers" escrow model: buyer funds are captured into the platform Stripe account (no transfer_data/application_fee on the PaymentIntent), held in escrow, and released to the brand's Connect account minus commission via releaseEscrow() when an order is marked delivered+paid. A daily Vercel cron (08:00 UTC, CRON_SECRET-protected) charges due installments off_session. Disputes are raised by buyers/brands and resolved by admins; "resolved_refund" only flips the order to refund_approved (no automated Stripe refund or transfer clawback).

Overall health: the happy path works, but the money-movement code is NOT fault-free and is unsafe for a multi-currency, multi-brand, installment marketplace. The most serious problems: (1) releaseEscrow pays ONE brand the FULL order total for orders that can legally contain items from multiple brands; (2) escrow auto-releases the entire order total to the brand after only the FIRST installment succeeds, because any single succeeded PI flips payment_status to 'paid'; (3) no Stripe idempotency keys on transfers.create or installment paymentIntents.create, and no DB row-lock/conditional-update or unique constraint, so retries/concurrency cause double payouts and double charges; (4) refunds and disputes never reverse the Stripe transfer or claw back commission, and there is no hold/return window before release. Note on the suspected currency bug: I verified it is NOT a fault. total_usd is a misnamed column that actually holds the order total in the order's own currency (the multi_currency migration comments confirm orders/payments carry their real currency and amount), so grossCents and the EUR/GBP transfer currency are consistent. Flagging it would be a false positive.
